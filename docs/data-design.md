# Stella Sora 共有データの設計（下書き）

> 状態：**下書き**（2026-11-04）。まだ何も実装していません。決まったら、この文書をもとに `docs/shared-data.md`（公開用の仕様）を書き直します。
> 「決めること」は最後の章にまとめています。

---

## 1. 目的

- 計算ツール（巡遊者の計算ノート）、プリセット共有サイト、**ほかのファンサイト**が、同じデータを同じルールで使えるようにする。
- やり取りするのは次の2種類。
  - **資料データ**：巡遊者・素質・ロスレコ・徽章などの「ゲームの事実」と、その解釈
  - **編成データ**：誰かの編成（巡遊者・素質Lv・徽章・ロスレコなど）
- 場当たり的に作らず、更新・修正・共有の流れまで決めておく。

## 2. 基本の方針

1. **データの元は自分たちで持つ。** 公開のデータリポジトリ（仮称 `stellasora-data`）を1つ作り、計算ツールもプリセット共有サイトもそこから取る。
2. **Wiki はデータの元にせず、分かったことを書き込む先にする。** こちらで確かめた値は、人の手で日本語Wikiに書き込む。Wiki の文章は配るデータに入れない（7章）。
3. **持っていない項目は書かない。読む側は、読めるものだけ読む。** 資料データ・編成データの両方で同じ（4章）。
4. **値ごとに出典と確かさを持つ。** ゲームの画面・Wiki・実測のどれから来たか、いつ誰が確かめたか。
5. **データの出どころは、ゲームの画面・公開Wiki・自分たちの実測だけ。** ゲームのファイルの解析はしない。
6. **データベース（D1）ではなく、JSON ファイル＋git。** 量が小さく更新もたまになので、変更履歴とレビュー（PR）がそのまま残るほうがよい。D1 は、利用者からの報告の受付など、書き込みが多いものだけに使う。

## 3. データの層

| 層 | 例 | 出典 | 確かさの扱い |
|---|---|---|---|
| A. 名前・ID | 巡遊者のID、日本語名・英語名、素質の枠の位置 | ゲームの画面、ゲームのプリセットコード | ほぼ確定。違えば直す |
| B. 事実 | 素質の説明文の数値（Lv1・Lv6）、徽章の品質ごとの値、ロスレコの数値 | ゲームの画面、Wiki | `source` と `verified` を必ず付ける |
| C. 実測 | ダメージ式、係数、敵の耐性、検証の記録 | 自分たちの測定 | 測った条件（徽章の有無など）を付ける |
| D. 解釈 | `effects`（計算ツールが使う効果の分類） | このプロジェクト独自 | `status`（confirmed / draft など） |

- 層ごとにファイルを分ける。ほかのサイトは「A だけ使う」といった使い方ができる。
- A は全員の共通語（キー）なので、いちばん慎重に扱う。

## 4. 共通のルール（資料データ・編成データの両方）

### 4-1. 項目の省略と読み込み

- **必須の項目は、ファイルの `schema` と、各レコードのキー（`id`）だけ。** ほかはすべて省略してよい。
- 持っていない項目は **書かない**。`null` も書かない（`null` は「値が無いと確かめた」という意味に取っておく）。
- 読む側は：
  - 知らない項目は **無視する**（エラーにしない）。
  - 読めなかったもの（知らないID、形の違う値）は **飛ばして、一覧で知らせる**。
  - 足りない項目は、読む側の初期値で埋める。
- 版（`schema`）は、互換性が壊れる変更のときだけ上げる。項目を足すだけなら上げない。

### 4-2. キー（ID）

| 対象 | キー | 理由 |
|---|---|---|
| 巡遊者 | ゲームのID（数値。例：セイナ = 112） | ゲームのプリセットコードに入っている番号なので、画面から確かめられる |
| 素質 | `巡遊者ID` + `role`（main / support）+ `slot`（枠の番号） | プリセットコードの並び順と同じ。名前が変わっても変わらない |
| ロスレコ | 英語名から作った短いキー（例：`mirai`） | ゲーム内の番号を画面から確かめられないため |
| 徽章の項目 | 計算ツールの `EMBLEM_OPTIONS` の `key`（例：`elemDmg`） | 同上 |
| 敵 | 短いキー（例：`stomp`） | 同上 |

- 名前（日本語・英語）は **キーではなく属性**。IDを持たないサイトのために、名前で照合する方法も書いておく（4-4）。
- 一度公開したキーは変えない。消すときは `deprecated: true` を付けて残す。

### 4-3. 出典と確かさ（どの層の値にも付けられる）

```json
{ "value": 0.6, "source": "game", "verified": "2026-10-30", "by": "freiheit", "note": "Lv6・絶流・波紋" }
```

| 項目 | 意味 |
|---|---|
| `source` | `game`（ゲームの画面）／`measured`（実測）／`wiki_ja`／`wiki_en`／`interp`（補間・推定） |
| `verified` | 確かめた日（YYYY-MM-DD） |
| `by` | 確かめた人（任意。ハンドル名） |
| `status` | 解釈の層の確かさ：`confirmed` `builtin` `draft` `review` `none` `unclassified` |

- 値だけでよいときは、ただの数値で書いてもよい（`"lv6": 0.6`）。出典を付けたいときだけ、上の形にする。

### 4-4. 名前で照合するとき

- 全角・半角、空白、「・」の有無をそろえてから比べる。
- 日本語名が一致しなければ英語名で比べる。それでも決まらなければ「読めなかった」に入れる（似た名前に当てない）。

## 5. 資料データ（リポジトリの構成）

```
stellasora-data/
  README.md            使い方・ライセンス
  schema/              JSON Schema（形のチェック用）
  v1/
    trekkers.json      A: 巡遊者（ID・名前・属性・レア度・役割）
    potentials.json    A+B: 素質（枠・名前・Lv1/Lv6の数値）
    effects.json       D: 素質の効果の分類（計算ツール独自）
    records.json       A+B: ロスレコ
    emblems.json       A+B: 徽章の項目と、品質ごとの値
    enemies.json       C: 敵（耐性・防御など、実測）
    formula.json       C: ダメージ式の係数（実測）
    changelog.md       データの更新の記録
```

- 1つのファイルの形は、どれも同じ：

```json
{
  "schema": 1,
  "updated": "2026-11-04",
  "license": "CC-BY-4.0",
  "items": [ { "id": 112, "...": "..." } ]
}
```

- 今の `data/shared/potentials.json` は、`potentials.json`（A+B）と `effects.json`（D）に分ける。
- 計算ツールの `data.js` や `sim_data.js` の中にある値（徽章・ロスレコ・敵）も、順にここへ移す（9章）。

## 6. 編成データ（新しく作る）

サイトどうしで「この編成」を受け渡すための、人が読める JSON。今の共有コード（短い英数字）はそのまま残し、辞書も変えない。これとは別のもの。

```json
{
  "format": "stellasora-build",
  "schema": 1,
  "from": "https://sim.stella-tool.com",
  "team": [
    {
      "trekker": 112,
      "level": 90,
      "potentials": [ { "role": "main", "slot": 1, "lv": 6 }, { "role": "main", "slot": 0, "core": true } ],
      "emblems": [ { "kind": "triangle", "slots": [ { "key": "elemDmg", "q": "rainbow" } ] } ],
      "skills": { "basic": 10, "main": 10, "support": 10, "ult": 10 }
    }
  ],
  "records": { "main": ["mirai"], "sub": ["negai"] }
}
```

- `team` の並び：1人目が主力、2・3人目が支援（ゲームのプリセットコードと同じ）。
- 徽章を扱わないサイトは `emblems` を書かない → 計算ツールは徽章を空にして読み込む。
- 素質だけのサイト（プリセット共有サイトなど）は `trekker` と `potentials` だけでよい。
- 受け渡しの方法：
  - ファイル（`.json`）を読み込む
  - 貼り付け（Ctrl+V）
  - URL：`sim.html#build=<JSONを圧縮してBase64URLにしたもの>`（長すぎるときは短縮URLを使う）
- 計算ツールは、読み込んだあとに「読み込めたもの／飛ばしたもの」を一覧で見せる。

## 7. Wiki との関係

- 日本語Wiki（wikiru）の文章はライセンスがはっきりしないため、配るデータには入れない。必要なら、出典のURLだけを持つ。
- 英語Wiki（miraheze）は CC BY-SA の可能性が高い。使うなら、出典を書き、別のファイルに分ける（ほかのデータのライセンスに混ぜない）。
- こちらでゲームの画面・実測で確かめた値は、日本語Wikiに書き込む（人の手で）。Wiki とゲームの画面が違うものの一覧を、リポジトリで持っておく。

## 8. 更新と修正の流れ

1. 直したい人は、PR か Issue を出す（ほかのサイトの人も同じ）。
2. GitHub Actions で、JSON Schema による形のチェックと、キーの重複・消えたキーのチェックを自動で回す。
3. `edit.html`（今の素質の効果の編集ページ）を、データリポジトリ向けの変更を書き出す道具にする。
4. 公開：`main` に入ったら、Cloudflare Pages で `data.stella-tool.com/v1/...` に配る。
   - CORS を許可する（ほかのサイトがブラウザから直接読めるように）。
   - キャッシュは短め（データの直しがすぐ届くように）。
5. `changelog.md` に、使う人に関係する変更を書く。

## 10. 決めること

1. **連携したい相手のサイト**は決まっているか（決まっていれば、相手の形に寄せる）。
2. **ライセンス**：CC BY 4.0（出典を書いてもらう）か、CC0（条件なし）か。
3. **Wiki の文章**を配るデータに含めるか（下書きでは含めない）。
4. **データリポジトリを公開にするか**（GitHub の公開リポジトリにするか）。
5. **ロスレコ・徽章・敵のキー**を、今の計算ツールのキーのままにするか（下書きではそのまま）。
6. **編成データの範囲**：心相・凸・Lv・スキルLv・信頼レベルまで入れるか。
